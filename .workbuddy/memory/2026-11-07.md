## 18:05 code-quality-review：排班/打卡全链路审查与修复（提交 7a06d00）

用户问「排班正常吗、操作方便吗、改了排班会实时修改吗、打卡」。审查结论与修复：

1. **改排班不会实时改日报（已修）**：schedules.service 增删改从不触发重算，日报行是生成时刻的排班快照；每日 02:00 cron 只重算「昨天」，改更早的排班后日报永远旧口径。修法：五个写路径后对受影响 (员工,日期) 调 `recalculate({employeeId,...})`（该接口本就支持按员工过滤，一直没人调），**只重算 workDate < 今天的日期**——当天日报可能只有单张上班卡，引擎按首末卡推算会把「上班中」写成 early/absent 瞬时值；当天以打卡路径为准（打卡实时查排班），次日 cron 兜底。每对独立 try/catch（月报已确认被拒不阻断排班写入）。
2. **[Blocker] selfSchedule 可洗迟到（已修）**：`attendance:view` 权限即可调、无「仅无排班时」限制；引擎 `lateMinutes = first > start ? diff : 0` 无提前窗口校验 → 迟到员工把今日班次改成很晚时刻，下次重算即洗白。修法：已有排班拒绝（「今日已有排班，如需调整请联系考勤管理员」）。前端 punch.tsx 入口本就只在无排班时显示（`!(shift && hasSchedule && !isRestDay)`），后端是最终防线。
3. **clockOut 沿用 existing.status 的脏状态（已修）**：status 初值改从 lateMinutes 推导（保留迟到标记），正常下班顺带修正为 normal。
4. entrypoint-boot-chain 单测同步昨日 Dockerfile 改动（.next/cache 已是 BuildKit 挂载点，rm 只删 standalone）。

**排班页 UX 评价（未改动）**：schedule-calendar.tsx 已很成熟——印章模式（选班次点格盖章）、批量原子（batch upsert + batchRemove）、破坏性确认、请假拦截、乐观更新 + 防抖 revalidate、roving tabindex（3100 格只有 1 个 Tab 停靠点）。操作便利性没有明显短板。
