# ADR-0011: 算薪消费"已确认的考勤月报快照"（含例外调整通道）

- 状态：已接受（Accepted）
- 日期：2026-08-12

## 背景

自动算薪引擎需要一个确定的输入。两种候选：

- **方案 A（实时算）**：算工资时实时读取每笔打卡/请假/加班数据计算。
- **方案 B（快照算）**：月末考勤先"结账"生成并锁定月报，工资基于锁定快照计算。

**实时算的问题**：结账后任何补录（补卡、修正排班）都会改变工资数字——工资不可复现、无法对账，员工质疑时无据可查。**快照算的问题**（用户提出）：员工存在忘记打卡（漏卡）、迟到等现实情况，是否会与"锁定"冲突？

## 决策

**采用方案 B：算薪引擎只消费"已确认（confirmed）的考勤月报快照"**，不读取实时打卡数据。同时配套"结账前后双通道"解决漏卡/迟到等现实问题：

1. **结账前（正常路径，数据可随便改）**：
   - 月度周期内，漏卡/迟到等异常随时处理：员工提交补卡申请 → 走审批流 → 批准后修正考勤日报并留痕（补卡人/原因）
   - 迟到扣款属常规路径，已在月报中累计（late_minutes），天然包含
   - 月末 HR 核对异常（缺卡/迟到/申诉中）**处理完毕后**才点"确认月报"——结账是人工确认动作，不是系统自动锁定

2. **结账后（例外路径，不污染快照）**：
   - 结账后才发现的漏卡等，**不回头修改已锁定的月报**
   - 通过 `payroll_adjustments` 调整项在工资层面修正：记录 员工/项目/调整金额/原因/操作人，留痕可审计
   - 最终工资 = 锁定快照计算值 + 调整项

## 备选（已排除）

- 方案 A（实时算）：工资随补录数据漂移，不可复现、不可对账，否决。

## 后果

- 正向：工资数字稳定可复现，随时可重算对账；"确认月报"动作天然逼着 HR 发钱前核对考勤；例外修正全程留痕。
- 成本：月末多一步"确认月报"的人工操作；结账后新增的考勤修正只能走工资调整项（不能改月报），需要 HR 接受这个工作习惯。
- 约束：月报确认后锁定（attendance_monthly.status = confirmed）；调整项独立存表（payroll_adjustments），不覆盖 payroll_details 计算值。
