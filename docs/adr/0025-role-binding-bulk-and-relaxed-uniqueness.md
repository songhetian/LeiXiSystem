# ADR-0025: 适用角色批量设置，并放开「同模块一角色一流程」的唯一约束

- 状态：已接受（Accepted，部分取代 ADR-0024 第 2 条）
- 日期：2026-11-06
- 关联：ADR-0020（业务流程绑定与兜底顺序）、ADR-0024（流程 → 适用角色）、`backend/src/approval/role-workflow.service.ts`、`frontend/src/features/approval/pages/role-workflow.tsx`

## 背景

ADR-0024 把「职责授权」翻成「流程 → 适用角色」，并同时加了两条规则：页面逐条保存、同一 module 内一个角色只能绑一条**启用**流程（冲突码 `6317`）。

上线当天暴露出两个问题，都是「配一次要点 13 次」：

1. **只能逐条保存**：13 条流程，每条都要点开多选框勾角色。管理员真正想要的往往是「这套角色套用到全部流程」或「先按模块铺一遍再微调」。
2. **「一键全部覆盖」和唯一约束互斥**：考勤有 4 条流程（申诉/请假/加班/补卡）、员工事务有 6 条，全都属于同一个 `module`。只要把「普通员工」一次性套到全部流程，同模块内就必然出现重复绑定，`6317` 直接拦下 —— 用户要的那个快捷操作在现行规则下**不可能成立**。

再看 `6317` 想防的问题：兜底解析 `resolveWorkflowForUser` 已经带 `orderBy: { workflowId: 'asc' }, take: 1`，同一申请重复发起始终落到同一条流程，**不存在「随机」**。它防的是一个不存在的风险，代价是让配置入口基本不可用（一个角色在同模块只能待在一条流程里，等于请假、加班、补卡三选一）。

## 决策

1. **放开同模块唯一约束**：不再拦截「同一角色出现在同模块的多条流程里」。确定性由解析侧的 `orderBy workflowId + take 1` 保证，并在 ADR-0024 第 4 条与代码注释里写明「兜底固定取 ID 最小的一条」。`ERROR_CODES.APPROVAL_ROLE_WORKFLOW_CONFLICT(6317)` 与其文案一并删除 —— 留一个永不抛出的错误码只会误导后来人。
2. **新增批量接口** `PUT /approval/role-bindings/batch`，body `{ workflowIds, roleIds, mode }`，`mode ∈ replace | append | remove`：
   - `replace`：清空这批流程的旧绑定，再写入「流程 × 角色」笛卡尔积；`roleIds` 为空表示**清空这批流程的全部角色**（合法但破坏性，页面必须挂警示色）。
   - `append`：只补不删（`skipDuplicates` 兜住重复）。
   - `remove`：只删「这批流程 × 这批角色」的交集，不动其它角色的绑定。
   - **单事务**：不是前端循环调单条接口。13 条流程各发一次请求时中途失败会留下「一半新一半旧」，管理员无从判断该重试哪些；且每次都要跑一遍角色校验，N 次往返叠加后点一次保存要等好几秒（实测单事务 13 条 × 3 角色 ≈ 170ms）。
   - 前置校验全部在写之前：流程必须存在且未删除（差几条写进 `detail`）、角色必须存在、`append/remove` 必须给角色、`workflowIds` 为空直接拒绝（否则等于作用到全库）。
3. **页面改成按业务模块分组的行列表**，并给两级快捷：
   - 行内：「全部角色」「清空」，一条流程一次点击搞定；
   - 页头「批量设置」+ 每个模块头「本组批量设置」：范围（全部流程 / 某个模块）× 角色集（可全选）× 方式（覆盖/追加/移除），落库前用一句话说明后果（「将把「全部流程」13 条流程的适用角色设为：HR、管理员」/「将清空…」）。
   - 保存失败留在弹窗内并报错，不关窗（关掉就看不到哪一步没成）。

## 后果

- 正向：「一键默认全部覆盖」成为可行操作，13 条流程从 13 次点选降到 2 次（打开弹窗 + 保存）。
- 正向：配置粒度回到业务事实 —— 一个角色可以同时适用请假、加班、补卡，这本来就是真的。
- 代价：同一角色绑定同模块多条流程时，兜底解析取哪条由 `workflowId` 最小决定，语义上是「先建的那条优先」。这是**兼容兜底路径**的既定行为（ADR-0020 优先：业务已配置流程时根本不走这里），已在代码注释与页面「配置规则」浮层中写明。
- **仍未覆盖**（沿用 ADR-0024 的结论）：`approval_workflows.code` 仍唯一 —— 一个业务编码只有一条流程，因此绑定只在「该业务未配置流程」时才真正改变路由。要支持「同一业务按角色走不同流程」（请假：员工版/主管版），需放开 code 唯一并在解析处按角色择一，属独立变更。
